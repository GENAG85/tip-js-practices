## 2. Цель работы

Подключить браузерное приложение со списком задач к учебному HTTP API и реализовать получение и изменение данных через `fetch`.

В работе используются:

- `GET`, `POST`, `PATCH` и `DELETE`;
- JSON-тело запросов;
- `async` / `await`;
- `ApiError` для разных видов ошибок;
- тайм-аут и `AbortSignal`;
- состояния интерфейса `loading`, `ready`, `empty`, `error`;
- повторная загрузка списка после изменения данных на сервере;
- защита от устаревших ответов при нескольких быстрых запросах.

## 5. Структура решения

### `src/api-client.js`

Общий HTTP-клиент. Он:

- собирает URL и query-параметры;
- отправляет `GET`, `POST`, `PATCH`, `DELETE`;
- сериализует JSON-тело;
- добавляет необходимые заголовки;
- отдельно обрабатывает HTTP-, сетевые ошибки, тайм-аут и отмену;
- возвращает `null` для ответа `204 No Content`.

### `src/task-api.js`

Предметный API для задач. В нём находятся операции:

```text
getTasks
getTaskById
getCategories
loadInitialData
createTask
updateTask
setTaskCompleted
deleteTask
resetDemoData
```

Фильтры передаются серверу как query-параметры. Успешные ответы дополнительно проверяются на ожидаемую структуру.

### `src/form-validation.js`

Проверяет данные формы до отправки запроса:

- `title` — строка длиной 1–100 символов после `trim()`;
- `priority` — `low`, `medium` или `high`;
- `categoryId` — существующая категория.

### `src/task-view.js`

Создаёт карточки задач. Названия выводятся через `textContent`, поэтому серверная строка не интерпретируется как HTML.

### `src/app-controller.js`

Хранит текущее состояние приложения и связывает API с представлением.

После изменения данных используется схема:

```text
действие пользователя
→ POST / PATCH / DELETE
→ успешный ответ сервера
→ повторный GET с текущими фильтрами
→ обновление интерфейса
```

Поэтому сервер остаётся источником истины, а `localStorage` в ПР6 для хранения задач не используется.

## 6. Асинхронные состояния

Используются четыре состояния списка:

| Состояние | Значение |
|---|---|
| `loading` | запрос выполняется |
| `ready` | данные успешно получены |
| `empty` | запрос успешен, но подходящих задач нет |
| `error` | загрузка завершилась ошибкой |

Во время изменяющей операции кнопки временно блокируются через `setMutationPending(true)` и разблокируются в `finally`.

## 7. Защита от устаревшего ответа

При новой загрузке предыдущий запрос отменяется через `AbortController`.

Дополнительно каждой загрузке присваивается номер `loadSequence`. Результат применяется только в том случае, если его номер соответствует последней запущенной загрузке.

Это не позволяет более медленному старому запросу заменить результат более нового фильтра.

## 8. Индивидуальный вариант 8

Начальный фильтр:

```js
{
  completed: false,
  priority: "high",
  categoryId: 2,
}
```

При открытии:

```text
http://127.0.0.1:5506/?dataset=variant
```

должны отображаться невыполненные задачи высокого приоритета из категории 2.

Индивидуальный сценарий:

1. Создать задачу с `priority = high` и `categoryId = 2`.
2. Новая задача должна появиться в текущей выборке.
3. Перевести её в выполненные.
4. Выполняется `PATCH`, затем повторный `GET` с текущими фильтрами.
5. Так как фильтр содержит `completed=false`, выполненная задача исчезает из списка.

## 11. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при 404 или 500?**  
   Потому что HTTP-ответ был успешно получен. Поэтому необходимо отдельно проверять `response.ok`.

2. **В каком порядке обрабатывается ответ?**  
   Сначала `response.ok`, затем специальный случай `204`, потом `Content-Type`, после этого JSON.

3. **Чем `POST` отличается от `PATCH`?**  
   `POST` создаёт новую задачу, а `PATCH` частично изменяет существующую.

4. **Зачем нужен статус 201?**  
   Он сообщает, что новый ресурс успешно создан.

5. **Почему для 204 не вызывается `response.json()`?**  
   У ответа `204 No Content` нет тела, поэтому попытка разобрать JSON завершилась бы ошибкой.

6. **Зачем CORS?**  
   API и приложение работают на разных портах и считаются разными origin. API должен разрешить запросы браузерного клиента.

7. **Чем `empty` отличается от `error`?**  
   `empty` — корректный ответ без результатов, `error` — запрос не удалось выполнить или обработать.

8. **Почему `localStorage` больше не источник задач?**  
   В ПР6 состояние принадлежит серверу. Клиент получает актуальный список через API.

9. **Зачем повторный GET после мутации?**  
   Чтобы отрисовать состояние, подтверждённое сервером, с учётом текущих фильтров.

10. **Как возникает гонка запросов?**  
    Старый медленный запрос может завершиться после нового и попытаться заменить более свежие данные.

11. **Почему одного AbortController недостаточно?**  
    Источник данных может завершить запрос несмотря на отмену, поэтому дополнительно проверяется номер загрузки.

12. **Почему отмена не отображается как ошибка?**  
    При смене фильтра отмена предыдущего запроса является ожидаемой частью управления приложением.

13. **Что проверяется на клиенте и сервере?**  
    Клиент проверяет форму для удобства пользователя, но сервер обязательно повторно проверяет входные данные.

14. **Зачем контроллер получает `view` параметром?**  
    Это отделяет бизнес-логику от DOM и позволяет тестировать контроллер без браузера.

15. **Почему используется `textContent`?**  
    Чтобы текст от сервера не интерпретировался браузером как HTML-разметка.

## 12. Вывод

В ПР6 браузерный интерфейс был подключён к учебному HTTP API. Реализованы чтение, создание, редактирование, изменение статуса и удаление задач. После каждой мутации интерфейс повторно получает данные с сервера, поддерживает состояния загрузки и ошибок и защищён от устаревших ответов при быстрых последовательных запросах.
