## Эксперимент с очередями выполнения

Базовый прогноз для меток A–F: `A → B → C → D → E → F`.
После добавления собственной микрозадачи G ожидается: `A → B → C → D → E → G → F`.

Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственная микрозадача
F: задача таймера
```

A, B и C относятся к синхронной части. Продолжения Promise и `await` выполняются как микрозадачи после завершения синхронного кода. Таймер с задержкой `0` не выполняется сразу: его обработчик становится отдельной задачей и выполняется после доступных микрозадач.

## Наблюдение за HTTP-ответом

Для запроса незавершённых задач высокого приоритета:

| Свойство | Фактическое значение | Что означает |
|---|---|---|
| URL запроса | `/api/tasks?completed=false&priority=high` | Фильтры переданы серверу в query-параметрах |
| Метод | `GET` | Получение данных без изменения состояния сервера |
| Статус | `200` | Запрос выполнен успешно |
| `response.ok` | `true` | Статус входит в диапазон 2xx |
| `Content-Type` | `application/json; charset=utf-8` | Сервер вернул JSON |
| id полученных задач | `[4, 13, 34]` | Результат серверной фильтрации |
| `meta.total` | `3` | Количество элементов в `data` |

Дополнительные наблюдения:

- `/api/health` → `200`, JSON `{ data: { status: "ok" } }`;
- `/api/tasks/25` → `200`, объект задачи id 25;
- `/api/tasks/999` → `404`, `TASK_NOT_FOUND`.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый локальный учебный HTTP API |
| `src/api-client.js` | Формирование URL, `fetch`, JSON, тайм-аут, отмена и единый тип ошибок |
| `src/task-api.js` | Маршруты задач и категорий, фильтры и проверка схемы данных |
| `src/variant.js` | Номер варианта и его фильтры |
| `src/main.js` | Контрольный консольный сценарий |

`fetchFn` передаётся в `createApiClient`, чтобы клиент можно было проверять без настоящей сети. HTTP-ошибки обрабатываются после получения `Response`, а сетевые ошибки перехватываются только вокруг самого `fetch`, поэтому ошибка `404` не превращается в `network`. После `response.json()` структура данных дополнительно проверяется, потому что корректный JSON ещё не гарантирует соблюдение контракта API.

## Классификация ошибок

| Сценарий | `kind` | Фактический результат |
|---|---|---|
| Задача `999` | `http` | `status=404`, `code=TASK_NOT_FOUND`, `details={ id: 999 }` |
| `completed=yes` | `http` | `status=400`, `code=INVALID_QUERY` |
| `/debug/error` | `http` | `status=503`, `code=SERVICE_UNAVAILABLE` |
| `/debug/invalid-json` | `invalid-response` | Ошибка разбора JSON |
| `/debug/text` | `invalid-response` | Неверный `Content-Type` |
| Не запущен API | `network` | Ответ от сервера не получен |
| Задержка больше тайм-аута | `timeout` | Превышено время ожидания |
| `AbortController.abort()` | `aborted` | Запрос отменён вызывающим кодом |

## Доменный модуль задач

| Вызов | Фактический результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]` |

Для задачи проверяются: положительный безопасный `id`, непустой `title` до 100 символов, boolean `completed`, допустимый `priority` и положительный `categoryId`. Для категорий проверяются `id` и непустое название. В коллекциях проверяются уникальные id, а `meta.total` должен совпадать с длиной массива.

Для двух независимых запросов с задержкой 120 мс получены следующие значения при контрольном прогоне:

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 302.0 | 246.4 | 247.1 | Вторая операция начинается после первой |
| `Promise.all` | 125.1 | 127.5 | 122.7 | Независимые запросы выполняются одновременно |

Точные значения времени зависят от компьютера. Важен порядок запуска: при `Promise.all` оба Promise создаются до общего ожидания.

## Отладка

Основные точки для отладки клиента:

1. перед вызовом `fetchFn`;
2. после получения `Response`;
3. перед `response.json()`;
4. в обработке HTTP-ошибки;
5. в классификации сетевой ошибки, тайм-аута и отмены.

Для успешного запроса `/tasks` проверяются URL, `status=200`, `ok=true` и JSON `Content-Type`. Для `/tasks/999` получается `ApiError` с `kind="http"`, `status=404`, `code="TASK_NOT_FOUND"`.

## Вывод

В работе реализован переиспользуемый HTTP-клиент на `fetch` и предметный API задач. Отработаны `Promise`, `async/await`, `Promise.all`, query-параметры, HTTP-статусы, JSON, сетевые ошибки, тайм-аут и явная отмена запроса. HTTP-ошибка отличается от сетевой тем, что при HTTP-ошибке ответ от сервера получен, но его статус не входит в 2xx. Неверный формат ответа классифицируется отдельно как `invalid-response`.
